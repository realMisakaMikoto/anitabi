# v0.2.0 现场验收操作单

这份操作单只覆盖无法由模拟器或远程假定位代替的三项现场证据。它不会把“代码已有策略”误写成“真实环境已通过”。采证脚本只读 ADB 状态，不改系统设置、不操作路线、不读取 ORS Key，也不上传位置或日志。

## 开始前

1. 使用公开签名版 `cn.anitabi.navigator` v0.2.0；脚本会核对手机中 `base.apk` 的 SHA-256 是否等于公开 Release 资产。只在 App 内填写已重新生成、未在聊天或 Git 中暴露的个人 ORS Key。
2. 手机开启 USB 调试并授权当前电脑。运行 `adb devices -l`，设备必须显示为 `device`。
3. 证据默认写入 Windows 临时目录 `anitabi-field-evidence`，不要提交到 Git；其中可能含设备状态和最近位置。
4. 先在 App 内生成路线并点“开始连续导航”，确认常驻通知存在，再启动脚本。脚本不会代替用户选择路线或制造到站事件。

脚本示例：

```powershell
.\scripts\capture-field-evidence.ps1 -Scenario gnss -DurationMinutes 90 -IntervalSeconds 60
```

可用场景为 `gnss`、`oem`、`transit`。有多台设备时加 `-Serial <adb序列号>`；ADB 不在 PATH 时加 `-AdbPath <adb.exe绝对路径>`。

## A. 真实 GNSS 的 8–12 点路线

前置条件：

- 在开发者选项中把“选择模拟位置信息应用”设为“无”，并停用假定位应用。脚本发现仍有应用获准 `android:mock_location` 时会拒绝开始。
- 在安全、适合步行或驾车的户外区域选择 8–12 个真实可达点。不得为了验收违反交通规则或进入受限区域。

步骤与证据：

1. 截图记录路线预览中的模式、点数、总距离和起终点，不包含 ORS Key。
2. 开始连续导航后运行 `-Scenario gnss`，时长覆盖整段行程。
3. 保留至少一次中途导航截图和最终“路线已完成”截图；记录是否出现错误重算、漏到站或错误自动到站。
4. 查看 `summary.json`、`samples.csv`、`location-end.txt` 与 `crash-buffer-end.txt`。

只有同时满足以下条件才记为通过：真实完成 8–12 点；Android 没有把位置标为 mock；全部点按顺序自动推进并完成；前台服务和通知采样无缺口；无本应用崩溃；语音在需要提示时可听。若使用手动到达，只能把对应点记录为手动回退验证，不能冒充自动 GNSS 到站。

## B. 小米/OEM 数小时后台与省电

前置条件：

- 记录测试开始时该 App 的小米电池策略、系统省电模式、剩余电量和是否充电。不要为了得出“通过”而临时关闭原本要验证的 OEM 策略。
- 先开始一条尚未完成的连续导航路线。

步骤与证据：

1. 运行 `-Scenario oem -DurationMinutes 180 -IntervalSeconds 60`；该场景低于 120 分钟会被脚本拒绝。
2. 锁屏并按真实使用方式携带手机。期间不要从最近任务划掉 App，也不要手动结束导航。
3. 结束后解锁并打开 App，截图记录路线仍可恢复、当前进度和常驻通知。
4. 查看 `samples.csv` 中的 `servicePresent`、`notificationPresent`、PID 变化、Doze/息屏状态，以及 `batterystats-end.txt` 和崩溃缓冲。

只有持续至少两小时、真实经历息屏/Doze、路线与进度最终仍可恢复、服务和通知没有无法解释的缺口且无本应用崩溃，才记为通过。PID 改变本身不直接判失败；如果 Android 重启了进程，必须确认 `START_STICKY` 与 Room 恢复后的路线、进度正确。

## C. 真实错过公交班次后的自动重算

前置条件：

- 选择 Transitous 有数据、包含至少一次非步行换乘的真实行程；确保等待和观察位置安全。
- 不通过修改系统时间、伪造 API 响应或假定位制造“错过”。一次初始规划加一次事件触发重算即可，不要反复刷新公共 API。

步骤与证据：

1. 截图记录原路线的当前段、下一班非步行交通的计划发车时间和换乘信息。
2. 开始连续导航并运行 `-Scenario transit`，在真实换乘处不登上原定班次，让计划发车时间自然过去至少两分钟。
3. 截图记录 App 自动进入重算状态以及新的剩余行程/新发车时间；若网络不可用，应记录“保留旧路线”的明确提示。
4. 记录实际时间、站点、原班次、新班次、是否由用户点了手动刷新，并检查 `summary.json`、服务/通知与崩溃缓冲。

只有原班次在现实时间中确实已错过、用户没有先点手动刷新、App 自动请求并展示了按当前时间生成的新剩余行程，才记为自动重算通过。仅有单元测试、把系统时间调快、或手动刷新都不能替代这项现场证据。

## 结果登记

每次现场运行在 `docs/PHYSICAL_DEVICE_ACCEPTANCE_v0.2.0.md` 追加日期、设备/系统版本、场景、路线点数或班次、起止时间、结果、证据目录的本机位置和异常说明。不要提交原始位置日志、截图中的个人信息或任何 API Key；仓库只记录脱敏结论和必要哈希。
