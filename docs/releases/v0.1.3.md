# v0.1.3 发布验收记录

核对日期：2026-07-29

结论：Transitous 公交已按官方政策启用。此前项目把“对请求负载有疑虑时联系维护者”错误升级为“必须取得明确批准”，并在构建、网络和 UI 中设置硬门槛；v0.1.3 已删除该门槛，保留真实的低负载边界，并完成公开固定签名发布。

## 已通过并有直接证据

- [x] 重新读取 <https://transitous.org/api/>：政策要求 FOSS/非营利、best-effort、正式 API、可识别 User-Agent、开源代码和可见数据来源链接；对潜在高负载或负载有疑虑的用法要求/建议提前联系，但没有“等待明确批准”的条件。
- [x] 项目已于 2026-07-29 通过官方 Matrix 房间说明最多 8 点、逐段串行、用户操作触发、本机缓存、无爬取/分析/广告的低频用途。该联系记录不再充当功能审批开关。
- [x] `ANITABI_TRANSITOUS_APPROVED`、对应 `BuildConfig` 字段、API 拦截异常、ViewModel 状态与 UI 禁用逻辑全部删除；发布工作流也不再读取该变量。
- [x] 生产端点固定为 `https://api.transitous.org/api/v6/plan`。新增单元测试验证 GET 参数、正式路径契约和 `AnitabiNavigator/0.1.3 (https://github.com/realMisakaMikoto)` User-Agent。
- [x] 公交最多 8 个巡礼点；超限在任何行程请求前拒绝。逐段请求在同一协程中串行执行；网络层关闭连接失败自动重试；应用不做后台轮询、批量下载或并发抓取。
- [x] 一次真实东京两点请求返回 9 条可选行程，首条包含 3 个路段；测试只发送 1 个请求，没有轮询、并发或重复探测。

## 证据边界

- 单次东京查询证明正式端点、请求参数、User-Agent 和服务响应可用，不代表日本所有地区、日期或运营方都有数据。
- 单元测试证明请求契约、8 点上限和串行时间链；模拟器回归证明启用公交后没有破坏现有应用启动与导航运行时，但不能替代实体手机上的完整公交实走。
- v0.1.0、v0.1.1、v0.1.2 的 APK 确实因项目误读而关闭公交；历史发布文档已保留事实并加注纠正，不能反过来解释为 Transitous 官方要求批准。
